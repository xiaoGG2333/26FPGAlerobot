# 验证阶梯与调试方法

## 双胞胎法（本方法论的核心）

同一个数值定义写两份实现，链进**同一个可执行文件**，对同一批输入比对，要求 **0 LSB 差异**。

- 一份是「好写的」功能模型：`std::vector` 缓冲、`double` 缩放、直白写法。
- 一份是「综合形状的」实现：`static` on-chip 数组、定点、pragma、整数偏移。

价值：在没有 RTL 仿真、没有工具链、也没有板子的情况下，把 RTL 之前所有算术风险提前消掉。而且失败时能二分——功能模型对 ORT 绿了，那双胞胎的差异一定是「综合形状」那一版引入的。

命名建议：两份实现用不同 namespace / 不同输出缓冲区前缀（`gen_HM_BUF`），避免符号冲突，才能同时链进去。

## 阶梯与判据

| 级 | 比什么 | 判据 | 失败含义 |
| --- | --- | --- | --- |
| V0 | numpy 定点参考 vs ORT int8 | 热图 mean ≤ 0.5 LSB；**每个输出头**都对 | 定点语义理解错 |
| V1 | C++ 功能模型 vs ORT int8 | mean ≤ 1.0 LSB，max 几 LSB | 层表/参数/布局错 |
| V2 | HLS 形状实现 vs 功能模型 | **0 LSB**，N/N 帧 | 结构改写引入的错 |
| V3 | HLS csim 打印值 vs g++ 值 | 一致 | 前端/宏/路径问题 |
| V4 | 综合报告 | `SYNCHK 200-77`=0、DSP≠0、Latency≠0、时序收敛 | HLS 没理解你的代码 |
| V5 | 板子 | 预处理一致 + 端到端延迟 | 集成问题 |

**V0/V1 允许 LSB 级差异，V2 不允许。** 因为 V2 两侧做的是完全相同的整数运算，任何差异都是 bug。

## 定位「第一处发散」

不要猜，用逐层 trace：

1. 给两份实现各加一个 `#ifdef` 的 trace，打印每层输出缓冲区的 `shape/min/max/mean`。
2. 编译成一个同时打开两个宏的可执行文件，把两份 trace 并排 diff。
3. **对齐偏移是最容易错的地方**：功能模型的 trace 常常打「应用本层之前的缓冲」，而 HLS 侧的 trace 打「本层自己的输出」，所以 `HLS L(i)` 对应 `functional L(i+1)`。搞反了会一路错位，看起来每层都不对。
4. 第一个数值不同的层就是问题层。

同理，在 ONNX 侧做逐层 dump：把所有 `QuantizeLinear` 的输出都加进 graph outputs，ORT 跑一次，逐层和 numpy 参考 diff——比通读代码快得多。

**症状学**：修完一处之后数字**一模一样**地错，说明这条代码路径不是活的缺陷（或者被饱和掩盖了）。别在原地继续改，换一条线索。饱和到 255 特别擅长掩盖下游差异：尾部 GAP 饱和时，FC 的输出和输入几乎无关。

## 三个「测量异常」的识别规则

1. **恰好为 0**：先怀疑双重单位换算。真实案例：把已经 ROI 归一化的坐标又除了一次 256，两个模型的差异全部变成 0.00%，看着像完美逐位一致。修完单位后是 0.34% ~ 0.50%。
2. **离线指标与肉眼观感差 20 倍**：先怀疑测量路径（颜色通道、角点/中心约定、插值方向、尺寸不匹配），不要先怀疑模型。真实案例：离线 NME 0.74 而现场演示看着挺好，最后是协议/裁剪路径的问题。
3. **两个来源「互相一致」不等于对**：让同一个模型分别用两种模式跑，得到一致的标签，只说明它稳定，不说明它正确。

## 交叉验证的唯一可靠办法

**一次只变一个变量，并且变换同一份输入，而不是重新采集。** 想把「分辨率/压缩」这个变量隔离出来，就把同一段高分辨率视频下采样成目标分辨率，用完全相同的管线重建缓存再测。这样得到的结论（差 2%）才可信；重新录一段数据会把视角、光照、姿态全带进来。

## 常数要跟着数据走

演示程序里任何「训练集统计常数」（典型如 `尺度中位数`）都必须从当前缓存重算并传进去，不能跨数据集写死。写死的常数会造成一个隐蔽的正反馈：控制器用模型自己的预测去定尺度 → 模型有 10% 偏差 → 框每帧缩 5% → 一路缩到下限 → 模型在残缺裁剪里产生幻觉。凡是闭环里用模型自身预测当输入的控制器，都要**每帧限幅**（例如 ±5%），否则收敛点在下限。
